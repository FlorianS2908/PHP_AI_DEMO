Tag 1 · HTML, CSS und Bedienbarkeit

Erwartetes Arbeitsprodukt: Eine eigene HTML-Seite mit externer CSS-Datei und dokumentiertem Tastaturtest.

Erkläre am eigenen Code den Unterschied zwischen Tag, Element und Attribut.
Ein Tag markiert die Elementgrenze; zum Element gehören auch Inhalt und gegebenenfalls End-Tag; Attribute ergänzen Eigenschaften im Start-Tag.
Zeige eine CSS-Regel und benenne Selektor, Eigenschaft und Wert.
Zum Beispiel .hinweis ist der Selektor, color die Eigenschaft und navy der Wert.
Ordne Tastatur, Bildschirm und HTTP den passenden Schnittstellenebenen zu.
Tastatur: Eingabe; Bildschirm: Ausgabe; HTTP: Protokoll zwischen Softwarekomponenten.

Tag 2 · Formulare, GET und POST

Erwartetes Arbeitsprodukt: Ein beschriftetes Formular und je ein protokollierter GET- und POST-Aufruf.

Worin unterscheiden sich id und name?
id verbindet das Element unter anderem mit label und muss auf der Seite eindeutig sein; name bestimmt den übertragenen Schlüssel.
Wo findest du die Daten einer GET- und einer POST-Formularanfrage?
GET: Query-Teil der URL; POST: Request-Body, sichtbar in der Netzwerkanalyse.
Warum ist POST allein kein Schutz vertraulicher Daten?
POST ist eine Methode; Verschlüsselung kommt durch HTTPS. Server und Browserwerkzeuge können die Daten weiterhin verarbeiten bzw. anzeigen.

GET muss die Werte in der Query, POST im Request-Body zeigen. Ein ungesetztes Kontrollkästchen fehlt. name liefert den Schlüssel; die PHP-Lupe behandelt Array-Werte ohne Warnung.

Tag 3 · PHP-Grundlagen in kleinen Schritten

Erwartetes Arbeitsprodukt: Ein PHP-Skript mit Variablen, einer Entscheidung, einer Schleife und einer kleinen Funktion.

Was sieht der Browser vom PHP-Quellcode bei korrekter Serverausführung?
Der Browser erhält die erzeugte Ausgabe, etwa HTML, nicht den serverseitig ausgeführten PHP-Code.
Was bewirkt strict_types bei gewöhnlichen Variablen?
Es macht gewöhnliche Variablen nicht statisch typisiert. Es steuert strenge Regeln an skalaren Typdeklarationen.
Wie viele Durchläufe hat for ($i=1; $i<=3; $i++)?
Drei Durchläufe mit i = 1, 2 und 3.

Tag 4 · Formulardaten prüfen und auswerten

Erwartetes Arbeitsprodukt: Ein kleines Formular mit PHP-Verarbeitung, Fehlerliste, Wiederanzeige und Testprotokoll.

Warum reicht required im HTML nicht aus?
Der Client kann die Browserprüfung umgehen; der Server erhält auch manipulierte Anfragen.
Wann ist empty("0") problematisch?
Wenn 0 fachlich ein erlaubter Wert ist, darf er nicht als fehlend verworfen werden.
Warum beendet exit das Skript nach header("Location: ...", true, 303)?
Der Header allein beendet PHP nicht; exit verhindert ungewollte weitere Verarbeitung und Ausgabe.

Tag 5 · Cookies, Sessions und Kursabschluss

Erwartetes Arbeitsprodukt: Eine Cookie-Einstellung, eine Session-Übung und ein überprüftes kleines Formularprojekt.

Wo liegen Cookie-Wert, Session-ID und Session-Nutzdaten?
Cookie-Wert und Session-ID-Cookie: Browser; fachliche Session-Nutzdaten im Kurs: Server.
Warum zeigt $_COOKIE unmittelbar nach setcookie noch den alten Eingang?
$_COOKIE stammt aus der eingehenden Anfrage. setcookie beschreibt erst die ausgehende Antwort.
Was ist an deinem Projekt nach einem neuen Request noch vorhanden?
Das muss praktisch belegt werden: passende Cookies und Daten der gestarteten Session können weiterbestehen; gewöhnliche lokale PHP-Variablen beginnen je Request neu.
